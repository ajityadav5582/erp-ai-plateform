## 1. Table layout

Four tables, each with exactly one reason to exist:

| Table | Grain | Purpose |
|---|---|---|
| `purchase_orders` | one row per document | header, lifecycle state, denormalised totals |
| `purchase_order_lines` | one row per ordered item | commercial detail plus a frozen catalogue snapshot |
| `purchase_order_status_history` | one row per transition | append-only audit trail |
| `document_sequences` | one row per scope | concurrency-safe document numbering |

Every table carries `tenant_id` and `company_id`, matching
[`TenantScopedEntity`](../../inventory/application/src/main/java/com/erp/business/inventory/shared/domain/TenantScopedEntity.java),
which supplies the identity, audit and `version` columns via `OptimisticLock`.

## 2. Decisions and their reasons

### 2.1 Surrogate key, business number for humans

`id BIGINT GENERATED BY DEFAULT AS IDENTITY` is the primary key; `po_number` is
unique per `(tenant_id, company_id)` and is what the API and printed documents
use. Exposing a sequential id to users leaks volume information and produces
support tickets when a number is mistyped; the surrogate key exists only for
joins and foreign keys.

### 2.2 Line amounts are generated in the database

```sql
line_amount NUMERIC(19,4)
    GENERATED ALWAYS AS (ROUND(quantity * unit_price * (1 - discount_percentage / 100), 4)) STORED
```

Any Java-side total can be missed on one of the several paths that mutate a
line (grid edit, partial receipt, cancellation, import). A generated column is
recomputed by PostgreSQL on every write, so the stored amount cannot drift from
its inputs. The entity maps it `insertable = false, updatable = false` so a
stale in-memory value is never written back.

### 2.3 Catalogue attributes are snapshotted onto the line

`item_code`, `item_name`, `uom_code` and `tax_rate` are stored alongside
`item_id`. A purchase order is a contract. Renaming an item or changing its VAT
rate must never rewrite what a supplier agreed to, and a PO issued two years ago
must still print what it said. Live catalogue values are read from the
inventory service for reporting and are never written back.

### 2.4 No cross-service foreign keys

`supplier_id` and `item_id` point at the inventory service. They are plain
`BIGINT` columns with no `REFERENCES` clause. A database-level constraint across
a service boundary forces both services to migrate in lockstep and lets either
one block the other's deploy. Integrity is enforced where the knowledge lives:
the service resolves the supplier and item through the inventory client and
rejects ids outside the current tenant and company.

Within the aggregate, the opposite rule applies. `purchase_order_lines` and
`purchase_order_status_history` do declare foreign keys to `purchase_orders`,
with `ON DELETE CASCADE`, because a line without a header is meaningless.

### 2.5 Composite FK to prove tenant alignment

```sql
FOREIGN KEY (purchase_order_id, tenant_id) REFERENCES purchase_orders(id, tenant_id)
```

A foreign key on `purchase_order_id` alone would happily attach a line to
another tenant's order if the id were ever supplied by a client. Carrying
`tenant_id` in the key makes the database reject it. This required the
supporting `uk_purchase_orders_id_tenant` index.

The first draft expressed this as a `CHECK` containing a subquery. PostgreSQL
forbids subqueries in `CHECK`; the composite key is the correct mechanism.

### 2.6 Header totals are denormalised but never accepted from input

`subtotal_amount`, `discount_amount`, `tax_amount`, `shipping_amount` and
`total_amount` live on the header. Persisting them is a deliberate
read-performance trade: a list screen showing 50 orders would otherwise
aggregate 400 line rows. The invariant that keeps them honest is that
[`PurchaseOrder.recalculateTotals()`](src/main/java/com/erp/business/procurement/purchaseorder/domain/PurchaseOrder.java)
is the only code path that writes them, it is called after every line mutation,
and there is no setter for a total anywhere in the aggregate.

### 2.7 Numeric, never floating point

Amounts are `NUMERIC(19,4)` and quantities `NUMERIC(19,6)`, mapped to
`BigDecimal` with explicit scales. `double` would introduce rounding drift that
surfaces as totals off by a cent, which is unacceptable on a financial document.

### 2.8 Single currency per document

`currency` is on the header only. Lines have no currency column, so a
mixed-currency purchase order cannot be constructed by mistake, and no code path
needs the currency-mismatch guard that
[`Money`](../../libraries/common-core/src/main/java/com/erp/platform/common/model/vo/Money.java)
performs at runtime.

## 3. Lifecycle

```
DRAFT ──submit──▶ SUBMITTED ──approve──▶ APPROVED ──▶ PARTIALLY_RECEIVED ──▶ RECEIVED ──close──▶ CLOSED
                     │                        │                              │                     │
                     └──reject──▶ REJECTED    └──────── cancel ───────────────┴────── cancel ───────┘
```

Rules encoded in the domain, not in SQL:

- Lines are mutable only in `DRAFT`. `PARTIALLY_RECEIVED` and `RECEIVED` are
  reachable only through `receiveAgainstLine`, never through `transitionTo`.
- `REJECTED`, `CANCELLED` and `CLOSED` are terminal.
- Rejection and cancellation require a reason; an unexplained void is not
  auditable.
- A terminal state can never be reached from a terminal state, so a closed
  order cannot be reopened without a compensating document.

`chk_purchase_orders_status` restricts the *value set*. It cannot restrict
*transitions* without a trigger, which would move business rules into the
database where they are invisible to the application tests.

## 4. Index strategy

| Index | Serves |
|---|---|
| `idx_purchase_orders_tenant_company` | every scoped list query |
| `idx_purchase_orders_open` (partial) | open-order workbench and AP ageing |
| `idx_purchase_orders_supplier` | supplier drill-down, supplier scorecards |
| `idx_purchase_orders_fiscal_year` | period reports, dashboard totals |
| `idx_purchase_orders_supplier_name_trgm` (GIN) | fuzzy supplier search |
| `idx_purchase_order_lines_order` | loading a document with its lines |
| `idx_purchase_order_lines_order_item` (partial) | three-way match by item |
| `idx_purchase_order_lines_pending` (partial) | goods-receiving worklist |

Two rules behind the table:

1. **Every index leads with `tenant_id, company_id`.** The application never
   runs an unscoped query, so an index that does not lead with the scope is
   dead weight that bloats writes.
2. **Closed and cancelled rows are excluded via partial indexes.** Over time
   they become the majority of the table while being the rows nobody queries.
   A partial index keeps the hot index small and is cheaper to maintain than
   letting dead rows accumulate in it.

`pg_trgm` is already enabled platform-wide per
[`infrastructure/postgres/README.md`](../../../infrastructure/postgres/README.md),
so the GIN trigram index adds no extension dependency.

## 5. Numbering

`document_sequences` holds one counter per
`(tenant_id, company_id, document_type, period_key)`. The
`next_document_number()` function upserts the row and increments it; the row
lock taken by the `UPDATE` serialises concurrent callers, so two buyers
creating a purchase order at the same moment cannot produce the same number.

The allocation must run **inside the same transaction** as the PO insert. If it
were a separate transaction, a rollback would burn a number and the counter
would drift from reality. The alternative, `SELECT max(po_number) + 1`, is
unsafe under concurrency and is exactly the bug this table removes.

## 6. Concurrency

The inherited `version` column maps to JPA `@Version` via
[`OptimisticLock`](../../libraries/common-data/src/main/java/com/erp/platform/data/lock/OptimisticLock.java).
Two buyers editing the same draft produce an `OptimisticLockingFailureException`
on the loser rather than a silent lost update. The client should surface the
current version so the edit can be retried deliberately.

## 7. Rules for extending this schema

1. **Append-only migrations.** Never edit `V001` once applied. Add `V002`.
2. **New columns are nullable or have a default.** An existing deployment must
   survive the migration without a data backfill gate.
3. **New checks are additive.** Loosening an existing check means dropping and
   recreating it; state that in the migration comment.
4. **Every new table gets `tenant_id`, `company_id` and the audit columns.**
   Inherit from `TenantScopedEntity` and the columns arrive for free.
5. **Every new index leads with the tenant and company scope.**
6. **New child tables use the composite `(parent_id, tenant_id)` foreign key.**
7. **Never denormalise a value that the aggregate can derive.** Totals are the
   one accepted exception, and only because list-screen reads dominate.

## 8. Verifying the schema

[`_verify.sql`](../../../infrastructure/postgres/flyway/procurement/_verify.sql)
exercises the migration against a real PostgreSQL and prints a PASS or FAIL
line per assertion. It is not a Flyway migration; run it by hand against a
scratch database:

```bash
docker exec erpai-postgres psql -U erpai -d postgres \
  -c "CREATE DATABASE po_schema_check;"
docker cp infrastructure/postgres/flyway/procurement/V001__create_purchase_order_tables.sql \
  erpai-postgres:/tmp/V001.sql
docker exec erpai-postgres psql -U erpai -d po_schema_check -v ON_ERROR_STOP=1 -f /tmp/V001.sql

docker cp infrastructure/postgres/flyway/procurement/_verify.sql erpai-postgres:/tmp/_verify.sql
docker exec erpai-postgres psql -U erpai -d po_schema_check -f /tmp/_verify.sql
```

All 17 checks pass and the script is re-runnable. It covers the generated
column rejecting an application-supplied value, cross-tenant line attachment,
over-receipt, the status and currency constraints, tenant-scoped numbering, and
the `updated_at` trigger.

Two notes for anyone extending the harness:

- Wrap each negative test in its own `DO` block with an `EXCEPTION` handler.
  Savepoints are not permitted inside a `DO` block, and without the handler the
  first intentional violation aborts the transaction so every later check
  silently reports nothing.
- Address rows by natural key (`po_number`, `item_code`), never by a literal
  id. Identity sequences do not roll back, so ids differ on every run.

## 9. What is deliberately not here

- **Purchase requisitions.** A separate aggregate with its own lifecycle;
  a PO references one through the free-text `reference` until that module exists.
- **Goods receipt notes.** Owned by the inventory service. Receipts are
  recorded against PO lines, which is why `received_quantity` lives on the line.
- **Invoices and payments.** Owned by finance. The integration point is
  `outstandingAmount()`.
- **Multi-currency.** A single-currency document with an explicit conversion at
  the payment boundary, rather than a rate per line.
