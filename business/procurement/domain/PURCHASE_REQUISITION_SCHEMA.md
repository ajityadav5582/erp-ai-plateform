# Branch-Wise Purchase Requisition — Domain Model

Status: implemented as JPA entities, module compiles clean
Package: `com.erp.business.procurement.purchaserequisition.domain`
Related: [PURCHASE_ORDER_SCHEMA.md](./PURCHASE_ORDER_SCHEMA.md)

Schema is defined entirely through JPA mapping annotations. There is no Flyway
migration for this aggregate; DDL is generated by Hibernate from the entities
below.

---

## 1. Scope

A purchase requisition (PR) is the **internal demand capture** stage of
procurement, scoped per branch. It is not a purchase order.

| Document | Owner | Answers | Has supplier |
| --- | --- | --- | --- |
| Purchase Requisition | Branch requester / branch approver | "What does my branch need, and do I approve it?" | No |
| Purchase Order | Procurement buyer | "What did the company commit to buy, from whom, at what price?" | Yes |

`PurchaseRequisition` deliberately carries no `supplierId`, no supplier name and
no agreed unit price. Commercial selection happens later at RFQ stage, because:

- one requisition line is routinely split across several suppliers (partial award);
- one RFQ routinely consolidates lines from several branches;
- the price on a requisition is an **estimate** for affordability testing, never a
  commercial commitment.

Conflating estimate with contract price is the classic way procurement systems end
up paying the numbers someone typed into a request form.

## 2. Process

```
Branch request
  └─> DRAFT
        ├─ submit(chain) ──> SUBMITTED
        │                     ├─ approve (last step) ─> APPROVED ──convertToPO──> CONVERTED_TO_PO
        │                     ├─ auto-approve (no approval required) ─> APPROVED ──> CONVERTED_TO_PO
        │                     └─ reject ─────────────> REJECTED
        └─ cancel ────────────────────────────────────> CANCELLED

SUBMITTED ──cancel──> CANCELLED
```

Terminal states: `REJECTED`, `CANCELLED`, `CONVERTED_TO_PO`.

`SUBMITTED` is the whole of the approval queue. There is no separate
"pending approval" state and no "return for correction" outcome: a document that
an approver does not accept is rejected, and anything the requester still wants to
buy is re-raised as a new draft. Each step of a multi-step chain is audited on its
own `PurchaseRequisitionApproval` row, so the queue does not need a state per step.

### Two workflows, one switch

The company setting `purchaseRequisitionApprovalRequired` (see
[§12](#12-companyworkflowconfiguration)) chooses between:

| Setting | Submission produces | Who decides |
| --- | --- | --- |
| `true` (default) | `DRAFT → SUBMITTED`, waiting | An approver, via the policy chain |
| `false` | `DRAFT → SUBMITTED → APPROVED`, in one request | The system |

Both paths pass through `SUBMITTED`. There is no shortcut edge from `DRAFT` straight
to `APPROVED`, because collapsing the two would make the history claim a transition
the status machine does not permit, and would erase the submitter's own moment of
submission from the audit trail.

## 4. Scope Model

Every scoped entity extends `TenantScopedEntity`, which supplies:

- `tenant_id` — mapped `updatable = false`, so a row can never be migrated
  between tenants;
- `company_id` — written, not immutable, because a company-scoped row may be
  re-validated on update;
- `assignScope(tenantId, companyId)` — called only from the application service
  using values read from the authenticated request context, never from a JSON
  body, so a caller cannot write into another company by tampering with a payload;
- a `@PrePersist` guard that refuses to persist an unscoped row, because such a
  row would be invisible to every scoped query.

`PurchaseRequisition` adds `branch_id`:

```
tenant_id  ->  company_id  ->  branch_id
```

Branch is a first-class accountability dimension, not a reporting filter: branch
budget is consumed per branch, branch heads approve branch requisitions, and
company roll-up reporting aggregates from `branch_id`.

## 5. Aggregate Boundary

`PurchaseRequisition` owns, via `CascadeType.ALL`:

| Collection | `orphanRemoval` | Reason |
| --- | --- | --- |
| `lines` | `true` | A line has no meaning without its header; dropping the last reference should delete the row, not orphan it |
| `approvals` | `true` | Resubmitting a returned document replaces the chain wholesale rather than leaving stale steps from the previous attempt |
| `statusHistory` | **`false`** | Deliberate. A procurement document is a legal record; detaching a history entry must not silently delete it |

`PurchaseRequisitionApprovalPolicy` and `DocumentSequence` are **outside** the
aggregate. They are company-wide configuration shared by many documents, and
cascading them from a document would mean saving one requisition could rewrite
the approval rules for the entire company.

## 6. `PurchaseRequisition`

| Field | Type | Notes |
| --- | --- | --- |
| `prNumber` | `String(40)` | Unique per `(tenant_id, company_id, pr_number)` |
| `branchId` | `Long` | Required. Identity reference, no database FK |
| `departmentId` | `Long` | Optional cost centre within the branch |
| `fiscalYearId` | `Long` | Budget and period reporting |
| `requestedBy` | `Long` | Identity user id |
| `requestDate` / `requiredByDate` | `LocalDate` | `requiredByDate >= requestDate` enforced in `draft()` |
| `status` | `PurchaseRequisitionStatus` | `@Enumerated(STRING)`, length 30 |
| `priority` | `RequisitionPriority` | Does **not** affect the approval chain |
| `currency` | `String(3)` | Single currency per document; lines carry none |
| `estimatedSubtotalAmount` / `estimatedTaxAmount` / `estimatedTotalAmount` | `BigDecimal(19,4)` | Planning figures |
| `approvedTotalAmount` / `orderedTotalAmount` | `BigDecimal(19,4)` | Committed figures |
| workflow stamps | `Instant` / `String` | Null until the transition happens |

### Derived totals

There is no `setEstimatedTotal(...)`. [`PurchaseRequisition.recalculateTotals()`](business/procurement/domain/src/main/java/com/erp/business/procurement/purchaserequisition/domain/PurchaseRequisition.java:561)
is the single writer, called after every line mutation, so the header total
cannot disagree with the lines that produce it. Values are still persisted
because branch budget dashboards must not aggregate the line table on every read.

### Budget is consumed at approval, not at order

`recalculateTotals()` moves value into `approvedTotalAmount` only once the
document reaches a budget-consuming state. Estimating is free; committing budget
is not. Before approval, an approved quantity on a line is still a proposal and
must not be reported as committed spend.

### Conversion is a single, terminal act

`CONVERTED_TO_PO` is reachable only through
[`convertToPO(...)`](business/procurement/domain/src/main/java/com/erp/business/procurement/purchaserequisition/domain/PurchaseRequisition.java:737),
which the service calls after the line quantities and order links have been
written. There is no code path that sets it directly, so a header can never claim
a conversion the lines do not support. How much of the demand was converted is
answered by the line quantities and the order links, not by a header flag - which
is why there is no `PARTIALLY_ORDERED` state to keep in step with them.

### Concurrency

The inherited `version` column gives optimistic locking: two approvers acting on
the same document produce an `OptimisticLockingFailureException` on the loser
rather than a silent lost update.

## 7. `PurchaseRequisitionLine`

### Three quantities, not one

| Field | Meaning |
| --- | --- |
| `requestedQuantity` | What the branch asked for. Must be positive |
| `approvedQuantity` | What was granted. Never above `requestedQuantity` |
| `orderedQuantity` | What procurement has committed to buy. Never above `approvedQuantity` |

Collapsing these into one quantity is the most common way requisition modules go
wrong: it makes partial approval invisible and makes "how much approved quantity
is still un-ordered?" unanswerable.

### Catalogue snapshot

`itemCode`, `itemName` and `uomCode` are stored next to the `itemId` reference. A
requisition is a statement about what a branch needed at a point in time. Resolving
those values live would let a catalogue rename or unit-of-measure change silently
rewrite the meaning of approved history and of every budget report derived from it.

### Amounts are computed in Java, not generated in the database

[`approvedNetAmount()`](business/procurement/domain/src/main/java/com/erp/business/procurement/purchaserequisition/domain/PurchaseRequisitionLine.java:391)
and
[`approvedTaxAmount()`](business/procurement/domain/src/main/java/com/erp/business/procurement/purchaserequisition/domain/PurchaseRequisitionLine.java:403)
are pure functions over the stored inputs. This differs deliberately from
`PurchaseOrderLine`, whose amount is a database generated column: the requisition
header recalculates on every mutation and must see a value immediately, before the
entity is flushed, so a database-side calculation would not be readable until a
round-trip. Exposing the arithmetic as two methods keeps exactly one
implementation.

Both are driven by **approved** quantity, not requested. A requester asking for
100 who is granted 60 must not consume budget for 100.

### Invariants enforced in the aggregate

| Rule | Enforced by |
| --- | --- |
| Approval never exceeds the request | `approveQuantity()` |
| Over-ordering is rejected | `registerOrdered()` |
| Rejected and cancelled lines never order | `registerOrdered()`, `cancelLine()` |
| A line with ordered quantity cannot be cancelled | `cancelLine()` |
| Tax rate is 0 to 100 | `create()`, `changeDemand()` |

Over-ordering is rejected in the domain as well as by a database constraint so the
caller receives a message naming the line.

## 8. `PurchaseRequisitionApproval`

### The chain is snapshotted, not resolved live

Rows are written at submission from the effective policy. If the chain were
resolved from the policy at approval time, an administrator editing a threshold
while a requisition sat in the queue would retroactively change or skip a step on
a document already submitted. That is an audit failure, not a convenience
problem. Snapshotting freezes the obligation that existed at submission.

### Inapplicable steps are skipped, not deleted

Amount-band policies are evaluated in sequence and most do not apply to every
document. Inapplicable steps are marked
[`ApprovalAction.SKIPPED`](business/procurement/domain/src/main/java/com/erp/business/procurement/purchaserequisition/domain/ApprovalAction.java)
and kept, so the stored chain still reads as the complete policy that was applied.
Deleting them would leave an auditor unable to distinguish a deliberate skip from a
missing configuration.

### Exactly one assignee

`decide()` rejects `SKIPPED` as a post-submission decision: skipped steps are
created only by the policy resolver. A step names a user or a role, never both and
never neither — naming two people would leave each believing the approval is
theirs.

Rejection and return require a comment, so a requester always has something
actionable.

### The requester may approve

A user who raised the requisition is not excluded from deciding it. Recording a
decision needs two things and nothing else: the matching permission in the token
(`PR_APPROVE` to approve, `PR_REJECT` to reject) and being the step's assignee.

This is deliberate. A company of one or two people has no second pair of eyes to
ask, and a hard "you raised it, so you may not sign it" rule leaves their
requisitions stuck in `SUBMITTED` forever. A company that *does* want a second
pair of eyes configures it where the module already reads it: an approval policy
that names a different user or a role for the step. The requester is then simply
not the assignee, and the refusal happens without any special-casing.

### An approval nobody gave

`autoApproved(...)` is the fourth creation form and the only one that does not
begin `PENDING`. It is used when the company's workflow settings do not require
approval at all, and it writes `action = APPROVED`, `actedBy = "SYSTEM"` and a
fixed reason on the step.

The obvious shortcut here is to write the submitter's own id into `actedBy` —
they submitted it, so they "approved" it. That is precisely the confusion the
table exists to prevent: a reader would see a named approver and conclude a
second person looked at the spend. `SYSTEM` makes the absence of a human visible
in the row itself, and `isAutomaticallyApproved()` reports it from the marker
rather than from `approverId` being null, because an ordinary open-to-approvers
step also names nobody.

The row is written even though nobody was required. Omitting it would make an
approved requisition indistinguishable from one that skipped its chain; leaving it
`PENDING` would strand a document in a queue no one will ever clear. `submit()`
requires a non-empty chain, and a single completed step is what keeps "every
requisition has an approval record" true.

## 9. `PurchaseRequisitionOrderLink`

The real cardinalities are not one-to-one:

```
requisition 1 ──> n purchase orders      (consolidated, or split award)
line         1 ──> n purchase order lines (partial award across suppliers)
```

Neither can be expressed by a `purchase_order_id` column, hence a link table.

The **quantity lives on the link**, recording how much *this* order contributes to
*this* line. The invariant `SUM(link.orderedQuantity) == line.orderedQuantity` is
then checkable at the link level, and a partial award is a first-class record
rather than a subtraction.

There is **no mapped relation to `PurchaseOrder`**. A bidirectional `@ManyToOne`
would couple the two aggregates into a cycle and make both document types
unloadable independently. The reference is by id and resolved by the application.

## 10. `PurchaseRequisitionApprovalPolicy`

Company configuration, outside the aggregate.

Each row covers `[thresholdMinAmount, thresholdMaxAmount]`, where a null maximum
means open-ended. Bands are validated to be non-negative and properly ordered at
construction.

`branch_id` is **nullable**, meaning a company-wide default. Resolution is branch
policy first, company default as fallback, so a large branch can require an extra
sign-off without every small branch duplicating the company rule. Materialising
the default into every branch row would mean changing it N times, with silent
divergence between branches.

Disabling is soft (`active = false`), because a rule that once governed approvals
is part of the audit story even after the company stops applying it.

## 11. `DocumentSequence`

A counter table rather than a database sequence, because document numbers must be
partitioned per company and reset per fiscal year. A native sequence is global to
the database and can express neither.

Unique on `(tenant_id, company_id, document_type, period_key)`.

It deliberately does **not** extend `TenantScopedEntity`. That base class brings
optimistic locking and a `@PrePersist` scope check, neither of which fits a
counter: the row version would conflict with the lock the repository must take on
the counter itself.

**Concurrency.** Allocation must run under a pessimistic write lock, or an atomic
upsert, inside the same transaction as the document insert. Read-increment-write
is a lost-update race that yields duplicate document numbers — the most damaging
defect a numbering scheme can have, because duplicates make an audit trail
ambiguous.

## 12. `CompanyWorkflowConfiguration`

Per-company workflow switches, in
`com.erp.business.procurement.workflow.domain`. Outside the requisition aggregate
by design: it configures the workflow, it is not part of any document.

Table `company_workflow_configurations`, unique on
`(tenant_id, company_id)` — one row per company, not one per document.

| Column | Type | Meaning |
| --- | --- | --- |
| `purchase_requisition_approval_required` | `boolean` | `true` = an approver decides; `false` = approved on submission |

**Default `true` for an unconfigured company.** A company that has never been
configured has not decided anything about its spend control, and the only thing
inferable from silence is that it should behave as it did before the switch
existed. Defaulting to `false` would switch off an internal control for every
existing company the day the row's absence was first observed. The service applies
the default rather than the database, so the fallback is visible in one place
instead of being folded into a query.

**A missing row is not created by a read.** `get()` answers with the effective
value and writes nothing; only an explicit `update()` creates the row. Otherwise
every screen that merely checks the setting would be performing a write.

**PUT, not PATCH.** The client edits a whole form, so one replacement has one
meaning. A null field on the update is rejected rather than treated as "leave it" —
a client that forgot the property would otherwise switch a company's approval
requirement off without ever asking for it.

**Permissions.** Reading needs `PR_VIEW`, because requisition screens must know
whether an approval queue exists. Writing needs `PR_ADMIN`, not `PR_APPROVE`:
switching a spend control off is a governance decision about the company, not an
act of procurement. An approver can sign spend and still cannot turn the control
off.

**It changes future submissions only.** A document already waiting in an approval
queue keeps the chain it was submitted with. The setting is read at submission and
the chain is snapshotted there, so a company cannot retroactively approve work
that is already in someone's inbox.

## 13. Indexing

Declared in `@Table(indexes = ...)`; Hibernate emits these on schema generation.

**Header list/filter indexes lead with the full scope prefix**, because every
query is tenant- and company-scoped first:

```java
idx_purchase_requisitions_scope       (tenant_id, company_id)
idx_purchase_requisitions_branch      (tenant_id, company_id, branch_id, request_date)
idx_purchase_requisitions_approval_queue (tenant_id, company_id, status, submitted_at)
idx_purchase_requisitions_fiscal_year (tenant_id, company_id, fiscal_year_id, request_date)
```

**Child table indexes lead with the parent foreign key**, because the dominant
access is "load this requisition's lines":

```java
idx_purchase_requisition_lines_requisition (purchase_requisition_id, line_number)
idx_purchase_requisition_lines_item_consolidation (tenant_id, company_id, item_id, status)
```

**Approver inbox** is served by `approver_id, action`; **order links** are indexed
in both directions so "why does this PO exist?" and "what is still un-ordered?"
are each a single lookup.

Partial indexes on open states are intentionally **not** declared here: Hibernate
cannot express a partial index through standard JPA annotations. They should be
added as a `@org.hibernate.annotations.SQLRestriction`-free, dialect-specific
`CREATE INDEX ... WHERE` statement once the DDL strategy is settled, because the
open queues are hot and small while closed documents are the bulk of the table.

## 14. Cross-Service References

Following the existing platform convention, references to other bounded contexts
carry no database foreign key:

| Column | Owning service |
| --- | --- |
| `branchId`, `departmentId` | Identity |
| `approverId`, `approverRoleId`, `requestedBy` | Identity |
| `itemId` | Inventory |
| `purchaseOrderId` | Procurement (same service, separate aggregate) |

A cross-service database FK would couple two services' migration timelines and
make an Identity schema change a Procurement release. Validation belongs in the
application layer, where the referenced entity can be fetched and checked for
tenant/company membership.

## 16. Application Rules Still To Implement

The schema permits these states; the service layer must enforce the graph.

**Requisition**

- Editable only in `DRAFT` (`isEditable()`).
- `submit()` must, in one transaction: re-validate branch and item scope, re-check
  branch budget, allocate the PR number, resolve and materialise the approval
  chain, write `SUBMITTED`, and append a status history entry.
- Approve only if the acting user is the assignee of the **current** pending step,
  using `isCurrentStep(chain)`; a later step must not be actionable while an
  earlier one is open.
- `cancel()` allowed only while `orderedTotalAmount == 0`. Once quantity is
  ordered, remaining demand is closed rather than cancelled.
- `close()` requires ordered value to reach approved value, or an explicit
  close-with-shortfall reason.

**Line**

- `approvedQuantity` may be reduced at approval, never increased beyond the
  request without resubmission.
- `orderedQuantity` increments only through a `PurchaseRequisitionOrderLink`, in
  the same transaction, keeping `SUM(link.orderedQuantity) == line.orderedQuantity`.
- A line with ordered quantity cannot be deleted or cancelled.

**Scope**

- `tenantId` from the security context, never from the request body.
- `companyId` from the `X-Company-Id` header, validated to belong to the tenant.
  A missing company context is a hard error, not a default.
- `branchId` validated to belong to `(tenantId, companyId)`.
